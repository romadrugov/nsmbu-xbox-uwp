# R10 — compile the *real* complete NSMBU runtime for Xbox WindowsStore/UWP

## Verified existing hardware and build baselines

- Owner's Xbox Series S R7D package `0.9.3.0` (and both
  `checkpoint/r7d-0.9.3.0` GitHub branches) must remain untouched.
  That historical diagnostic UWP application executed game code but did
  not render an NSMBU engine frame.
- R8 #4 successfully **linked** the complete *desktop* Windows
  `nsmbu.exe` with all 93 owner-private USA_V0 translation units and
  full NSMBU Recomp Cafe OS/GX2/Vulkan code. It never ran on Xbox.
  It requires a temporary whole-function hook ABI adapter, which cannot
  reconstruct instruction-site hooks.
- User's R9 hardware log confirms Dozen Vulkan `1.2.354` on
  `Microsoft Direct3D12 (SraKmd_arden)`, supported graphics queue,
  one CoreWindow swapchain and `REAL VULKAN/DOZEN FRAME PRESENT PASS`.
  This was **one synthetic color frame**, not an NSMBU draw call.

## Real R10 implementation

In `xbox/r10/CMakeLists.txt`, compile actual 93 private game-code
chunks + `table.c`/`imports.c`, the upstream Cafe OS thread,
mutex, FS, hooks and scheduler sources, complete Cemu Latte GX2
shader translation, Vulkan backend, input, audio and overlay sources,
ImGui and the glslang shader compiler. Use Clang musttail, WinRT x64
WindowsStore ABI, not MinGW desktop DLLs. Store output is a set of
**static libraries**; this first compile target is not yet an Xbox app.

The actual SDL3 fork at `XboxEmulationHub/SDL3-uwp` commit
`ec2e0e7c77ec9a04437eb3ae884d62ae0e6129b4` must be built
separately with MSVC `cl.exe /ZW` because its WinRT window code uses
C++/CX (`ref class`, `Platform::Agile`) unsupported by ClangCL.
Both compilers share x64 Windows Store ABI; the private CI installs the
MSVC SDL3 static library and compiles game runtime through ClangCL.

`tools/xbox/patch_r10_sdl3_dozen.py` patches **only the pinned
open-source SDL3 CI working tree** to connect the real upstream
`SDL_Vulkan_LoadLibrary`, `SDL_Vulkan_GetInstanceExtensions`,
`SDL_Vulkan_CreateSurface` and corresponding unload/destroy methods
to the R9-validated packaged `vulkan_dzn.dll` ICD. Its surfaces
come from `CoreWindow` using the Smash4-patched Mesa Dozen WSI,
not an HWND. It must not be called a game frame by itself.

The actual NSMBU Vulkan backend is now guarded by `NSMBU_XBOX_UWP`:
request Vulkan 1.2 on the measured Series S driver and skip an
unsupported separate GamePad CoreWindow; desktop behavior is unchanged.

## Next major steps after UWP compilation succeeds

1. Link the real full engine archives into a **new** UWP executable
   based on the already-tested R9 CoreApplication and Dozen loader,
   not the existing R7D boot shell.
2. Supply an AppContainer-safe guest-memory implementation (desktop
   `core.cpp::mem::init` commits 4 GiB unconditionally and must not
   be used blindly on a memory-constrained Xbox). Link actual
   upstream Cafe OS, input, audio, Vulkan shader code and supporting
   libraries including LuaJIT and SDL3, adapting restricted Win32 API
   usages from actual link/runtime logs. R9 128 MiB storage-buffer
   range must be respected.
3. Mount the owner's **complete** `code/content/meta` game resources
   in the new app's LocalState; one `red-pro2.rpx` alone is not enough.
4. On the Xbox, obtain and verify the **first frame generated by NSMBU
   GX2**, through its Vulkan renderer, Mesa Dozen and D3D12.
   A synthetic clear, a PNG, a green CI, or a swapchain alone is
   not an NSMBU game frame.
5. Only after actual Mario frame: Xbox controller/VPAD mappings,
   then sound, levels, and performance. Correctly regenerate from the
   user's own RPX with proper hook-aware recompilation as needed for
   gameplay parity.

This is a large integration direction, not one more HLE function stub.
